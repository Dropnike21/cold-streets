## Applied catalog-model corrections

- 14 non-empty catalog primary keys were switched to `GENERATED BY DEFAULT AS IDENTITY` so both imported historical IDs and future rows can coexist.
- Source pseudo-JSON is preserved as `TEXT` rather than silently transformed.
- `users.password_hash` is nullable to support future Supabase Auth identities without storing a duplicate password hash in player state.
- The 35 inferred state tables are **working hypotheses**, not recovered original DDL.
- `users.supabase_auth_uid` now has an FK to `auth.users(id)`, retaining NULL for unmapped legacy players.
- `time_deposits_one_active_per_user` partial unique index enforces a single active deposit per player.

**Identity sequences for the currently imported catalog tables (achievements, credit upgrades, education tracks, gyms) were synchronized** after import using `setval`. Repeat this procedure for every remaining catalog whose historical primary keys are explicitly restored.

## Important security boundary

The Node.js game API **is not yet authenticated** and should not be placed on a public endpoint; its routes trust client-supplied player IDs and some payouts/prices. Supabase database access must remain server-only until verified JWT middleware and ownership checks are implemented. RLS protection on PostgREST does not automatically secure arbitrary Express API routes or a privileged Node database connection.
